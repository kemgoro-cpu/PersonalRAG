# Issue Clarification Rule

この文書は、Issue が曖昧な場合の確認ルールです。

Codex は、Issue の内容が曖昧なまま実装を始めてはいけません。
特に、仕様を勝手に補完すると既存仕様の破壊、手戻り、データ破壊、セキュリティ問題につながる場合は、実装前に人間へ質問してください。

## 1. 基本方針

Issue を読んだら、まず以下を確認してください。

- 何を実現したいIssueなのか
- 期待される動作は何か
- 現状の問題は何か
- 変更対象になりそうな範囲はどこか
- 既存仕様を変える可能性があるか
- 不明点を仮定して進めても安全か
- 人間に確認しないと危険な判断があるか

不明点があっても、すべて質問する必要はありません。
ただし、**仕様・データ・権限・運用に影響する不明点**は、勝手に決めないでください。

## 2. 質問すべきケース

以下に該当する場合は、実装前に人間へ確認してください。

### 仕様に関する不明点

- 期待する動作が複数解釈できる
- 入力仕様が不明
- 出力仕様が不明
- UI仕様が不明
- エラー時の挙動が不明
- 正常系と異常系の扱いが不明
- どこまでを今回のIssue範囲に含めるか不明
- 既存仕様を変える可能性がある
- 依頼者の意図と実装内容にズレが出そう

### データに関する不明点

- 既存データに影響する
- DBスキーマに影響する
- ファイル形式に影響する
- API 仕様に影響する
- データ移行が必要になる可能性がある
- データ削除、上書き、変換が発生する
- 同名ファイルや重複データの扱いが不明

### セキュリティ・権限に関する不明点

- 認証に関わる
- 認可、権限、ロールに関わる
- 個人情報や社内機密情報に関わる
- 外部コマンド実行に関わる
- ファイルアップロード、ダウンロードに関わる
- ログに機密情報が出る可能性がある
- 利用者ごとの見える範囲、操作できる範囲が不明

### 運用・保守に関する不明点

- 障害時の扱いが不明
- ログ出力方針が不明
- リトライ、タイムアウト、排他制御が必要か不明
- パフォーマンス要件が不明
- 複数ユーザー同時利用の扱いが不明
- 将来の保守性に大きく影響する
- 変更範囲が想定より大きくなりそう

## 3. 質問せずに進めてよいケース

以下の場合は、仮定を明記したうえで進めてよいです。

- 既存コードから仕様が明確に読み取れる
- 既存テストから期待値が明確に分かる
- 変更が局所的で、既存仕様を変えない
- 軽微な表示文言や内部処理の修正である
- 安全側の仮定で進められる
- 後で簡単に修正できる
- 依頼内容と既存実装の対応関係が明確である

ただし、推測で進めた場合は、最終報告に仮定内容を明記してください。

## 4. 質問の優先順位

質問は最大 5 個までに絞ってください。

優先順位は以下です。

1. データ破壊や既存仕様破壊につながる不明点
2. セキュリティ、認証、権限に関する不明点
3. 期待動作が複数解釈できる不明点
4. UI、入出力、エラー処理に関する不明点
5. テスト方針や完了条件に関する不明点

細かい実装方法や内部構造については、既存設計から判断できる場合、人間に質問せず進めて構いません。

## 5. 質問形式

質問するときは、以下の形式にしてください。

```md
Issue の内容に曖昧な点があるため、実装前に確認させてください。

## 確認したいこと

### 1. 不明点のタイトル

- 確認したい内容:
  -

- なぜ確認が必要か:
  -

- 選択肢:
  - A:
  - B:
  - C:

- 推奨:
  -

- 推奨理由:
  -
```

複数ある場合は、重要度が高い順に並べてください。

## 6. よい質問の例

```md
Issue の内容に曖昧な点があるため、実装前に確認させてください。

## 確認したいこと

### 1. CSV出力時に既存ファイルがある場合の扱い

- 確認したい内容:
  - 同名ファイルが既に存在する場合、上書きするのか、別名保存するのか、エラーにするのか。

- なぜ確認が必要か:
  - 上書きすると既存データを失う可能性があるため。

- 選択肢:
  - A: 上書きする
  - B: 日時付きファイル名で別名保存する
  - C: エラーにしてユーザーに確認させる

- 推奨:
  - B

- 推奨理由:
  - データ消失を避けつつ、ユーザー操作を増やさずに済むため。
```

## 7. 悪い質問の例

以下のような質問は避けてください。

### 調べれば分かることを質問する

悪い例:

```md
この関数はどこで使われていますか？
```

まずコードを調査してください。

### 選択肢がない丸投げ

悪い例:

```md
どう実装すればいいですか？
```

推奨案を添えてください。

### 質問が多すぎる

悪い例:

```md
確認したいことが 12 個あります。
```

最大 5 個に絞ってください。

### 技術用語だけで聞く

悪い例:

```md
この API は冪等性を担保しますか？
```

必要なら、業務上の意味も添えてください。

## 8. 質問後の進め方

人間から回答を得たら、以下を行ってください。

1. 回答内容を短く要約する
2. 実装方針に反映する
3. 必要なら `explorer` agent で再調査する（ユーザーが agent 利用を明示した場合のみ）
4. 必要なら設計確認を行う
5. 実装に進む

回答後も曖昧さが残る場合は、追加で質問してください。
ただし、追加質問も必要最小限にしてください。

## 9. 仮定して進めた場合の最終報告

仮定して進めた場合は、最終報告に以下を含めてください。

```md
## 仮定した内容

-

## 仮定した理由

-

## 人間に確認してほしい点

-
```

## 10. 判断に迷う場合

判断に迷う場合は、以下の基準に従ってください。

- データ破壊の可能性があるなら質問する
- セキュリティや権限に関わるなら質問する
- 既存仕様を変えるなら質問する
- 依頼者の意図とズレる可能性があるなら質問する
- 後戻りが大きいなら質問する
- 後で簡単に直せる軽微な内部実装なら、仮定を明記して進める
