# 設計確認手順

この文書は、実装前または実装中に設計判断が必要になった場合の手順です。

設計確認の担当は、ファイルを編集せず、設計方針の確認と提案だけを行ってください。
最終的な実装判断と修正は、Codex 本体が行います。

## 1. 基本方針

設計確認では、理想論よりも、以下を優先してください。

1. 既存仕様を壊さない
2. 変更範囲を小さくする
3. 責務分担を分かりやすくする
4. テストしやすくする
5. 障害時に原因を追いやすくする
6. 小規模な内製チームで保守しやすくする
7. 将来拡張しやすくする

ただし、将来拡張性のために現在の実装を過剰に複雑にしないでください。

## 2. 設計確認が必要なケース

以下に該当する場合は、設計確認を行ってください。通常は Codex 本体で実施し、ユーザーが agent 利用を明示した場合のみ適切な agent を使います。

- 変更範囲が複数モジュールにまたがる
- 責務分担が曖昧
- 既存設計と合わない可能性がある
- DB、ファイル形式、API 仕様に影響する
- セキュリティ、認証、権限に関わる
- エラー処理方針を決める必要がある
- パフォーマンスに影響する可能性がある
- 運用・保守に影響する
- テスト方針を先に決めた方がよい
- 実装方針が複数あり迷う
- 小さな修正に見えるが、将来の拡張に影響しそう
- ログ、監査、トレーサビリティに影響する
- 複数ユーザー同時利用に影響する
- データの整合性に影響する

## 3. 設計確認で見る観点

### Responsibility

- どのモジュール、クラス、関数が責務を持つべきか
- 責務が集中しすぎていないか
- UI、ビジネスロジック、データアクセスが混ざっていないか
- 既存の責務分担と整合しているか
- 共通化すべき処理と個別に持つべき処理が分かれているか
- 将来、担当者が変わっても理解しやすいか

### Data Flow

- 入力から出力までの流れが明確か
- データ変換の場所は適切か
- 副作用が分かりやすいか
- エラー時の流れが明確か
- データの保存、更新、削除のタイミングが明確か
- 途中失敗時に不整合が残らないか
- ログやエラー情報から原因追跡できるか

### Interface

- API や関数の引数・戻り値は分かりやすいか
- 既存互換性を壊さないか
- 呼び出し側に余計な負担をかけないか
- 将来の変更に耐えられるか
- エラーの返し方が一貫しているか
- 呼び出し側が誤用しにくいか

### Nonfunctional Requirements

以下の非機能要件を確認してください。

- Security
- Reliability
- Maintainability
- Testability
- Performance
- Operability

特に、社内利用ツールでは以下を重視してください。

- 権限管理
- 誤操作防止
- データ消失防止
- ログ確認のしやすさ
- 障害時の原因追跡
- 引き継ぎやすさ
- 手動復旧しやすさ
- 利用者が増えた場合の影響
- セキュリティ上の説明責任

### Small Team Fit

小規模な内製チームで運用しやすい設計を優先してください。

避けるべきこと:

- 過剰設計
- 複雑すぎる抽象化
- 理解しづらいフレームワーク依存
- テストしにくい構造
- 属人化しやすい構造
- ドキュメントなしでは運用できない複雑さ
- 小規模ツールに対する大規模アーキテクチャ導入
- 今回使わない汎用化

## 5. 推奨方針の選び方

推奨方針は、以下の優先順位で選んでください。

1. 既存仕様を壊さない
2. 変更範囲が小さい
3. 責務分担が分かりやすい
4. テストしやすい
5. 障害時に原因を追いやすい
6. 小規模チームで保守しやすい
7. 将来拡張しやすい

ただし、以下のような理由だけで複雑化しないでください。

- 将来使うかもしれない
- 汎用化できそう
- 設計として美しい
- 大規模システムならこうするべき
- フレームワークの思想としては正しい

今回のIssueで必要な範囲を優先してください。

## 6. 代替案の扱い

代替案は、原則として 2 から 3 個までにしてください。

各案について、以下を整理してください。

- 内容
- メリット
- デメリット
- 実装コスト
- リスク
- 今回採用するかどうか

最終的には、1つの推奨案を明確にしてください。

## 7. 設計相談後の進め方

Codex 本体は、設計確認の提案を確認し、以下を判断してください。

- Issue の範囲内か
- 実装コストが妥当か
- 既存設計と整合しているか
- 今回やるべきか、別 Issue に分けるべきか
- 人間に確認が必要か
- テストや検証が可能か
- 運用時の説明が可能か

人間確認が必要な場合は、実装前に質問してください。

## 8. 過剰設計を避けるルール

以下は原則として避けてください。

- 今回使わない汎用化
- 将来の可能性だけを理由にした大規模設計
- 抽象クラスやインターフェースの過剰追加
- 設定ファイルの過剰分割
- 小規模ツールに対する大規模アーキテクチャ導入
- 既存コードから大きく外れた設計
- テストや運用よりも設計美を優先すること
- 担当者が理解できない構造にすること

ただし、以下の場合は設計見直しを検討してください。

- 既存構造のままだと明確にバグを生む
- セキュリティリスクがある
- テスト不能になる
- 運用時の障害対応が困難になる
- 今回のIssue範囲でも責務分担が破綻する
- データ不整合やデータ破壊の可能性がある
- 利用者増加時に明確な問題が起きる

## 9. 人間に確認すべき設計判断

以下は人間に確認してください。

- 既存仕様を変える判断
- UIや操作フローを変える判断
- データ保存形式を変える判断
- 既存データの移行が必要な判断
- 権限や認証方式を変える判断
- 運用ルールに影響する判断
- 将来の開発方針に影響する判断
- セキュリティ方針に影響する判断
- 障害時対応や復旧方法に影響する判断
- 他部署や他チームとの責務分担に影響する判断

## 10. 最終報告への反映

設計確認を行った場合、最終報告に以下を含めてください。

```md
## 設計確認結果

- 採用した方針:
- 採用理由:
- 検討した代替案:
- 残リスク:
- 人間に確認してほしい点:
```

## 11. 判断に迷う場合

判断に迷う場合は、以下の基準に従ってください。

- 既存仕様を守る
- 変更範囲を小さくする
- テストしやすくする
- 障害時に原因を追いやすくする
- 小規模チームで保守しやすくする
- セキュリティ、権限、データ保護を優先する
- 過剰な汎用化を避ける
- 重要な仕様判断は人間に確認する
