# 差分レビュー手順

この文書は、実装後またはレビューのみを行う場合の手順です。

レビュー担当は、ファイルを編集せず、指摘だけを行ってください。
修正判断と実装は、Codex 本体が行います。

## 1. レビュー対象

原則として、現在のブランチと基準ブランチの差分を確認してください。
基準ブランチが不明な場合は、`main`、`master`、上流ブランチの順に確認し、どれを基準にしたか明記してください。

確認対象の例:

- 変更ファイル
- 追加ファイル
- 削除ファイル
- テスト差分
- 設定ファイル差分
- API 変更
- DBやファイル形式への影響
- エラー処理
- 権限・認証・セキュリティ関連

## 2. レビュー観点

以下を中心に確認してください。

### Correctness

- 期待仕様を満たしているか
- 条件分岐に漏れがないか
- null、空文字、空配列などの扱いは適切か
- 境界値に対応しているか
- 例外時の挙動は適切か
- 入力値の想定外ケースに対応しているか
- 既存仕様と矛盾していないか

### Regression Risk

- 既存仕様を壊していないか
- 既存 API の互換性を壊していないか
- 既存データへの影響はないか
- 他機能への副作用はないか
- 既存テストで守られていた挙動を変えていないか
- 一見関係ない画面・処理に影響していないか

### Security

- 認証・認可を迂回していないか
- 入力値検証が不足していないか
- 機密情報をログ出力していないか
- パストラバーサル、SQL インジェクション、XSS 等のリスクはないか
- 権限のないユーザーが操作できないか
- ファイル操作や外部コマンド実行が安全に扱われているか
- 個人情報や社内機密情報の扱いに問題がないか

### Tests

- 変更内容に対してテストがあるか
- 正常系だけでなく異常系も確認されているか
- 境界値のテストが必要ではないか
- 回帰テストが必要ではないか
- テストの期待値が仕様と合っているか
- テストが実装内容に依存しすぎていないか
- 手動確認が必要な場合、その観点が明確か

### Maintainability

- 責務が分かりやすいか
- 既存設計に合っているか
- 過度に複雑になっていないか
- 命名が誤解を招かないか
- 将来変更しやすいか
- 同じロジックが重複していないか
- エラー時の原因追跡がしやすいか
- 小規模な内製チームで保守しやすいか

## 3. 指摘の形式

指摘は、以下の形式で出してください。

```md
## Review Findings

### Finding 1

- Severity: high / medium / low
- File:
- Location:
- Problem:
- Why it matters:
- Suggested fix:
```

複数ある場合は、重要度が高い順に並べてください。

## 4. 重要度の基準

### high

以下に該当する場合は high としてください。

- 明確なバグ
- データ破壊の可能性
- セキュリティ問題
- 認証・認可の問題
- 本番障害につながる可能性
- 重大な既存仕様の破壊
- ユーザー操作で容易に再現する不具合
- 修正しないとリリースすべきでない問題

### medium

以下に該当する場合は medium としてください。

- 条件によって不具合になる
- テスト不足により回帰リスクが高い
- エラー処理が不十分
- 保守性が明確に悪化する
- 仕様が曖昧なまま実装されている
- 将来的に障害や手戻りにつながりやすい
- 一部の利用条件で問題になる可能性がある

### low

以下に該当する場合は low としてください。

- 軽微な保守性の問題
- 将来改善した方がよい点
- 命名や構造の軽微な違和感
- すぐに障害にはならないが改善余地がある点
- テスト追加が望ましいが、今回の変更範囲では必須ではない点

## 5. 指摘しないこと

以下は、重大な問題につながらない限り指摘しないでください。

- 単なる好みのスタイル
- 既存コードと同程度の軽微な癖
- 実害のないリファクタ提案
- 根拠のない仮説
- 「より良くできる」というだけの提案
- Issue範囲外の大規模改善
- 今回の変更と直接関係しない既存問題
- チームの既存ルールと矛盾する個人的な好み

## 6. 問題がない場合

重大な指摘がない場合は、以下のように明記してください。

```md
## Review Findings

重大な指摘はありません。

確認した観点:
- Correctness
- Regression Risk
- Security
- Tests
- Maintainability

注意点:
-
```

軽微な注意点がある場合は、「リリースを止める問題ではない」と分かるように書いてください。

## 7. レビュー後の対応

Codex 本体は、レビュー担当の指摘をすべて鵜呑みにせず、以下を判断してください。

- Issue の範囲内か
- 実害があるか
- 修正コストに見合うか
- 既存仕様を壊さないか
- 今回対応すべきか、別 Issue に分けるべきか
- 人間に確認すべき内容か

妥当な指摘のみ修正してください。
対応しない指摘がある場合は、理由を最終報告に書いてください。

## 8. 最終報告に含めること

レビュー後の最終報告には、以下を含めてください。

- レビュー担当が出した主な指摘
- 修正した指摘
- 修正しなかった指摘と理由
- 追加で実行したテスト
- 残リスク
- 人間に確認してほしい点
